# Contract & Renewal Tracker: Research Report

> **Where the code is.** The experiment scripts that produced these results are part of the source package, which is distributed separately (see [SOURCE-ACCESS.md](../SOURCE-ACCESS.md)). The raw results they wrote are included in this repository under [`results/`](../results/).

> **Status: protocol v0.2, results recorded (2026-11-23).** Questions, methods and the statistical plan were written down before the full experiments ran (v0.1); v0.2 adds the results and logs every deviation in the [change log](#11-change-log). **Every contract, vendor, owner and workload in this report is synthetic (generated by `crt.generator` and the experiment scripts); nothing was measured on a real company, real contracts or real people.** The numbers in section 7 are copied by a script from `results/summary.md`, which `experiments/summarize.py` generates from the raw per-run files in `results/`.
>
> **The product tracks dates and terms that a user enters. It does not read or interpret contracts and nothing in this report is legal advice.** Correctness below means "the computed dates follow the stated conventions", not "the dates are what any particular contract means".

## Abstract

This study asks four things about a small local contract and renewal tracker built on the Python standard library: (E1) does its date engine agree with an independent day-by-day reference; (E2) how much do reminder schedules and escalation change the fraction of notice deadlines missed when owners are simulated; (E3) does its CSV importer report or silently mangle damaged files; (E4) what request rate does the server sustain on the busy machine it was built on. Results on synthetic data only: (E1) 1,500 random contracts gave 5,147 events compared with **no disagreement**, as did 4,000 month additions and 600 deadline instants on daylight-saving change days; all 13 deliberately broken engines were caught, but the two that mishandle skipped or repeated clock hours were caught only by targeted samples, not by random cases; time-zone rules were not independently checked. (E2) In 216 simulated runs the missed-deadline rate for contracts the business wanted to cancel was 0.488 with one reminder, 0.172 with four and 0.064 with twelve; escalation cut these to 0.095, 0.043 and 0.023; twelve reminders with escalation was not distinguishable from four with escalation while sending about 1.2 times as many messages (798 against 652 per run); the owner behaviour is invented. (E3) Across 52 damage operators and 31,260 row outcomes, all 8,078 rows that had to be rejected were reported and all 23,182 harmless variants were imported unchanged; three deliberately lenient importers silently mishandled 7% to 10% of the must-reject rows, so the harness can see mangling. (E4) With one server process and a Python load generator on the same busy machine, median throughput was 13.8 requests/s with one client thread, 12.4 with four and 13.6 with eight, with no errors and p95 latency of 169, 952 and 1,945 ms. None of this predicts behaviour on real contracts or real people.

## 1. Research questions

- **E1.** Does the date engine (renewal dates, notice deadlines, deadline instants) agree with an independent brute-force reference over randomized terms that include month ends, leap years, business-day notice, holidays, odd weekends and daylight-saving changes, and is that comparison strong enough to catch deliberately broken engines?
- **E2.** How does the reminder schedule (A: one reminder, B: four, C: twelve) and the presence of escalation change the fraction of notice deadlines that are missed, when owners are simulated with limited attention, and how sensitive is the answer to alert fatigue?
- **E3.** When CSV files are damaged in many specific ways, how many bad rows does the importer report, and how many does it silently accept, change or drop?
- **E4.** What request rate does the local server sustain for a modest mix of UI and API requests on the (busy) machine it was built on?

## 2. Hypotheses

- **H1 (E1).** The engine agrees exactly with the reference on every generated case, and every deliberately broken variant is caught. (Expected weak spot to watch: random cases rarely land a deadline inside a skipped or repeated hour, so those two broken variants may need targeted samples.)
- **H2 (E2).** More reminders reduce missed deadlines, with diminishing or even negative returns when alert fatigue is strong; escalation helps most when the first reminders are ignored. Schedule A (one reminder) is clearly worst. These depend on invented behaviour parameters, so a no-fatigue and a high-fatigue scenario are included.
- **H3 (E3).** Because the importer accepts only ISO dates, plain-dollar amounts and fixed vocabularies, nearly every damaged row is reported, and harmless variants (BOM, CRLF, shuffled columns, whitespace, upper case) are imported unchanged. A lenient importer, by contrast, mangles rows silently, and the harness can see that.
- **H4 (E4).** The server handles a modest mixed workload at tens of requests per second on a loaded laptop-class machine without errors; throughput barely rises with client threads because database work is serialised behind one lock and pages are computed per request.

## 3. Background

- Auto-renewing contracts usually require notice some period before the end of the term; the period can be counted in calendar days, months or business days and different contracts treat weekends and holidays differently. This product's conventions are written at the top of `crt/dates.py` and in the README; they are one reasonable set of choices for a tracker, not legal rules.
- Month arithmetic needs a clamping rule (31 January plus one month); date libraries differ, which is why an independent walking reference is useful.
- Alert fatigue (people ignoring frequent automated messages) is a well-known effect; its size here is an assumption, not a measurement.
- Confidence intervals are percentile bootstraps (Efron and Tibshirani, 1993); paired comparisons use a sign-flip permutation test with Holm's correction (Holm, 1979); proportions use the Wilson score interval (Wilson, 1927).

## 4. Method

### 4.1 System under test

The implementation in this repository: Python 3.12 standard library, SQLite, `http.server`. The experiments use the same engine, alert, decision, escalation, import and web code as the UI.

### 4.2 Environment

Machine metadata and the system CPU load read before and after runs are stored in `results/*_meta.json`. Windows 11, AMD64 (8 logical CPUs as reported by the OS), CPython 3.12.13 chosen by `uv`, no third-party packages, `zoneinfo` unavailable (no IANA data), so time zones came from the rule-based stand-in in `crt/tz.py` (current US, EU, Australian-east and New Zealand rules applied to every year). **The machine was shared with other jobs and busy: the CPU load readings are quoted with each result.** E1 to E3 outcomes do not depend on machine load; E4 throughput and latency do and are probably pessimistic.

### 4.3 Experiments and baselines

- **E1.** The reference (`experiments/e1.py`, functions starting `r_`) adds months by stepping one day at a time to the target month, counts notice days and business days one day at a time, and finds each deadline instant by stepping UTC minutes until the local clock reads the cutoff. It shares with the engine only `datetime.date`, the holiday date sets and the time-zone object, so zone *rules* are not independently verified (they are unit-tested against hard-coded 2025 transition dates). Random cases: 5% start near the 2100 non-leap century, 5% on 29 February, 35% at month ends; terms and notice in days, weeks, months and years or business days; 0 to 25 holidays, half placed within 130 days before a renewal date; weekends Saturday-Sunday, Friday-Saturday or Sunday only; all three weekend-roll rules; cutoffs including 00:30, 01:30, 02:30 and 03:00; twelve zones. Four events per case are compared as full tuples (term start and end, renewal date, notice deadline, UTC deadline instant, end of the next term). Separately, 4,000 month-addition samples and 600 deadline instants chosen on daylight-saving change days (aimed at skipped and repeated hours) are compared. **Power check:** 13 deliberately broken engine variants (no month-end clamp, century leap-year bug, business-day off-by-one, holidays ignored, weekend hard-coded, weekend roll reversed, months as 30 days, weeks as days, fixed UTC offset ignoring daylight saving, drifting renewal dates, renewal one day early, repeated hour resolved to the second pass, skipped hour resolved late) are run over the same cases and samples; each must disagree with the reference somewhere.
- **E2.** The simulation drives the real product code day by day with an injected clock: the seeded portfolio generator, cycle and reminder materialisation, dispatch into the outbox, escalation rules and the decision workflow (cancel decision plus a notice recorded on or before the deadline date). Only people are simulated. Arms: schedules A `[30]`, B `[90,60,30,7]`, C `[90,60,45,30,21,14,10,7,5,3,2,1]` days before the deadline, each with escalation off or on (manager at 14 days and escalation contact at 3 days, for deadlines that still need action). Owner model (all invented): diligent / busy / overloaded owners (35% / 45% / 20%) see a notification with probability 0.92 / 0.70 / 0.40, multiplied by `exp(-fatigue * n)` where n is the number of notifications they received in the previous 7 days; a seen reminder on a contract the business wants to cancel leads to action with probability 0.90 / 0.80 / 0.60 after an exponential delay (mean 3 / 6 / 12 days); a seen reminder on a contract to keep is answered with a renew decision half the time; unowned contracts (5%) go to a shared mailbox seen with probability 0.35; managers and the escalation contact see escalations with probability 0.85 / 0.90 and act with 0.85 / 0.70. Intent: 35% of contracts are ones the business wants to cancel, at one uniformly chosen deadline in a 365-day window that starts after a 95-day warm-up (so every schedule runs in full). **Missed** = a cancel-intent contract whose notice was not recorded on time; the denominator is identical in every arm of a seed. Random draws are common across arms (keyed by seed, contract, deadline and message). 100 synthetic contracts per run, 20 seeds in the baseline scenario (fatigue 0.05) and 8 seeds each for no fatigue (0) and high fatigue (0.15).
- **E3.** A clean file of 60 synthetic contracts is exported; 52 damage operators each damage about 20% of rows (or the whole file) in one way; the damaged file is imported into a fresh tracker. For every affected row the expected behaviour was fixed in advance: **reject** (invalid or ambiguous data: impossible and day/month-swapped dates, European decimals, text where a number belongs, missing or extra fields, duplicates, over-length text, unclosed quote, wrong delimiter, bad encoding, NUL bytes ...) or **same** (harmless: BOM, CRLF, shuffled columns, whitespace, upper-case enumerations, quoted commas and newlines, unicode, an escaped formula prefix, `$1,234.50` amounts, blank lines, unknown extra column). Each affected row ends in one outcome: reported, accepted unchanged, accepted with changed values (silently mangled), accepted although invalid, lost (neither imported nor reported), or falsely rejected. 10 repetitions with different portfolios. **Power check:** the same operators are run against three deliberately lenient importers (permissive date parsing, a money parser that strips non-digits, a non-strict CSV reader).
- **E4.** `python -m crt serve` in its own process on 127.0.0.1 over a copy of a seeded synthetic database (150 contracts); a load-generator process with 1, 4 or 8 threads and keep-alive connections sends a fixed mix (15% dashboard, 20% contract list, 20% contract page, 10% API list, 10% API deadlines, 5% reports, 5% calendar, 5% timeline, 5% decision POST, 5% CSV validation POST) for 8 s after a 1.5 s warm-up; 5 repetitions per level, each with a fresh database copy and server. System CPU load is read just before every run.

### 4.4 Independent variables

Case features (E1), schedule, escalation and fatigue (E2), damage operator and importer variant (E3), client threads (E4).

### 4.5 Metrics

Disagreements (E1), missed-deadline rate with its split into never-aware and aware-but-late (E2), counts of rows by outcome (E3), requests per second and latency percentiles (E4).

## 6. Statistical plan

- **Replication:** E1 1,500 cases; E2 20 seeds (baseline) and 8 (sensitivity); E3 10 repetitions; E4 5 repetitions per level.
- **Summaries:** means (E2) or medians (E4) with percentile bootstrap 95% intervals (4,000 resamples over seeds or runs); Wilson 95% intervals for E1 and E3 proportions.
- **Comparisons:** E2 uses paired differences by seed against B with escalation, a two-sided sign-flip permutation test (exact up to 16 non-zero differences, Monte Carlo above) and Holm correction over the five comparisons in a scenario. No other tests.
- **Effect sizes:** the paired mean differences and their intervals; a statistically detectable but practically small difference is called small.

## 8. Reading the results

- **H1 (E1): supported, with one caution.** No disagreement anywhere, and every broken engine was caught. But random contracts almost never put a deadline in a skipped or repeated clock hour (6 deadlines on a DST-change day in 5,147 events), so two broken variants were invisible to them: without the targeted DST-edge samples the power check would have reported two escapes. The agreement is also only as strong as the reference's independence: the reference shares `datetime.date`, the holiday sets and the time-zone object with the engine, so a wrong zone rule would not show up here.
- **H2 (E2): partly supported inside the model.** More reminders reduced misses (one reminder is clearly worst; four is much better than one; twelve is better than four without escalation). With escalation the difference between four and twelve reminders was not distinguishable from zero in any scenario, while twelve sent about 1.2 times as many messages per run (798 against 652), which is a cost the model only charges through fatigue. Escalation helped at every schedule, most for the single-reminder schedule (0.488 to 0.095). The expected *negative* return from fatigue did not appear: even at fatigue 0.15 twelve reminders still missed fewer deadlines than four, because the model lets a seen reminder always have a chance to trigger action and charges nothing for annoyance beyond reduced attention. The sensitivity scenarios have only 8 seeds, so their intervals are wide and most Holm-adjusted p-values are not small.
- **H3 (E3): supported on these files.** No silent failure and no false rejection in 31,260 row outcomes; the lenient importers show the harness would have noticed. This is a statement about 52 operators the author thought of, not about every file a user could produce.
- **H4 (E4): not supported as worded.** Throughput was 10 to 18 requests/s, below the "tens" hypothesised, and did not rise with client threads; latency grew with threads, consistent with requests queueing behind one lock and the interpreter. The mix is dominated by pages that recompute every contract's timeline per request (no caching).

## 9. Threats to validity and limits

- **Synthetic everything.** Contracts come from `crt.generator` (invented tables of terms, notice periods and amounts); owners in E2 are invented; E3 files are damaged by the author's operators. No real contract, person or vendor was involved.
- **E1 independence.** The reference shares the date type, holiday sets and the time-zone object with the engine. The zone rules (current US, EU, Australian-east and New Zealand rules for every year, no history) are only unit-tested against 2025 transition dates. Conventions (renewal date, anchoring, notice counted back from the renewal date) are the author's and are not legal rules; E1 shows the engine follows them, not that they match any contract.
- **E1 coverage.** Only 4 events per random case were compared; holidays and weekends are random; there are no cases with notice longer than 2 years or terms longer than 5 years.
- **E2 model.** Every behaviour parameter is an assumption. Intent is one cancel per contract at one deadline. Managers are assumed to make the action happen. Reminder content is not modelled. Only the first 365 days after a warm-up are evaluated. Fatigue is the only cost of extra messages.
- **E3 expectations.** "Must reject" and "must accept" were decided by the author before the runs; reasonable people could accept some rejected inputs (for example `2025-3-4`). Operators damage about 20% of rows by one mechanism at a time; combinations are not tested. One of the operators (over-length text) only passes because the importer was changed to reject rather than truncate (see the change log).
- **E4.** One server process, load generator on the same machine, machine at 38% to 94% CPU load before runs, five repetitions per level, one run of the experiment. No profiling was done beyond one development-time look that led to the speed-ups listed in the change log. Absolute numbers are for this machine at that moment and say nothing about capacity elsewhere.
- **Not covered by any experiment:** the web UI's behaviour in browsers, accessibility, security, the IANA-zone code path (`zoneinfo` is unavailable here), and the behaviour of the alert check on a database with thousands of contracts.

## 11. Change log

- **v0.1** Protocol written (questions, hypotheses, methods, statistical plan) before the full runs.
- **v0.2 (2026-11-23)** Results recorded. Deviations and fixes made during the work, in the order they happened:
  - *E1:* the first small runs showed that random cases almost never put a deadline inside a skipped or repeated hour, so the 600-sample DST-edge set and two extra broken variants (repeated hour resolved to the second pass, skipped hour resolved late) were added before the full run. A unit test found that `\d` in the date, money and integer patterns accepted non-ASCII digits (for example Arabic-Indic numerals); the patterns were changed to `[0-9]` and `fullmatch` before E3 was written.
  - *E3:* the first tiny run exposed three things. Two operators were wrong (an "unpadded date" operator that sometimes changed nothing; operators that replaced a value on purpose without telling the checker the new expected value) and were fixed. One operator did not actually produce an unclosed quote and was rewritten. Two importer behaviours were changed because the experiment made them visible: over-length text (titles over 200 characters and so on) was silently truncated and is now rejected; an unbalanced quote used to report an error but also leave earlier rows imported while claiming "the rest of the file was not read", and is now a file-level error that imports nothing. The lenient-importer power check was added after the first clean result, to show the harness could see mangling.
  - *E2:* a pilot with 50 contracts per run had only about 8 contracts with cancel intent per run; the full run uses 100. Dispatch and escalation were changed to query only reminders and cycles near today (instead of reading every row each simulated day) so the simulation was fast enough to run; this does not change what they do.
  - *E4:* before measuring, two speed-ups were made after a one-off profile showed deadline-instant computation dominating page time: instants are no longer computed for past events, and the daylight-saving rule dates are cached. Page times fell by roughly a factor of three. The load generator starts the real interpreter (`sys._base_executable`) because a virtual environment's `python.exe` on Windows is a launcher that spawns a child process, and a test showed the child could still hold the database file after the launcher was stopped.
